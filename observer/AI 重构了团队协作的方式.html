现在是新人弯道超车的时机吗？ ​

本文没有实操的干货，只谈宏观的感受

我们团队长期使用 AI 来进行开发工作，效率确实得到了很多的提升，开发一直在各自打磨自己的 skill 和提示词，偶尔有人在做一些harness 工程的事情，但是也没有一个负责的人，因为很多东西都是在听在看，没有经过我们自己的验证，没有想要出头。所以我们对组织架构进行了调整。

这一次不是“大家都用 AI 辅助一下”，而是团队协作方式改变。

在去年超级个人，一人公司的概念喧嚣而上，似乎全民进入了一人公司的节奏中，底气就在于对于 AI 的信任，如下面的右边，一个在借助各个 agent 可以把一个公司的各个职能都闭环了。大半年下来，一人公司的狂热降温了很多，毕竟一个人能够干所有事情不以为他每一个都能干到 80 分，一个 80 分的软件不以为着是一个好的产品，一个好的产品也不以为着会带来期望的商业价值。

而且人脑的带宽是有些的，你无法对一个你毫不知情的职能业务输入有效的提示词，更加不用说形成固定的体系然后生成 skill 了，抄了网上的一些 skill 无法理解其中的理念就干用了？ 在没有 AI 的时代也不是这样的，不然每个人对于谷歌、小米、腾讯的协作方式抄就可以炒出一家腾讯公司来了么？

AI 压缩了实现时间，但没有压缩责任时间。

一个人就能够做成的事情商业价值也是有限的。所以为了干大事，我们主张的是超级个体之间的协作。

既然有协作，那么我们每个人的注意力就不是圆形，而是基于自身的能力去扩大自己的知识边界，理想目标是一个人负责一个模块所有的功能，但是回到上面说的情况，人的精力是有限的，所以依旧是需要分工。为了抹平个人之间对齐消耗的时间, 我们做了如下工作：

  1. 一个小组是 3 个人，开发、产品、UI；
  2. 开发作为负责人；
  3. 产品和 UI 是跨小组的，开发只对自己负责的模块负责；
  4. 开发和 UI 交付给开发的不是 PRD 、原型图、Figma 设计稿，而是一个原型项目；
  5. 开发作为这个项目最终实现漏底，UI 可以直接去修改生产的UI 设计。

大厂最消耗时间的事情就是对齐，因为实现的成本低，必须要确保所有的上下游的颗粒度都能够对齐一致

人类是视觉的动物，只要有想法，就可以很快的在生成一个可交互的原型图，并且这个原型项目是和生产的项目共用同一套的 UI 规范同一个 harness 工程的，所以一开始在需求评审的时候，大家看到的就比之前 PRD 或者原型图更加的直观，反馈一定是更加的快速的。

  1. 研发负责人开始承担更多项目经理角色

    这一次是研发负责人直接做项目经理，自己负责一个单独模块，而且是主要负责人。开发不只是开发，还要承担一部分产品、UI、测试，甚至还要承担需求推进。

  2. 一开始的设想是产品、设计也能直接写代码

    一开始的决策是：既然有 AI，那么产品、设计也应该可以直接实现代码。

    后来发现方向又变了。产品还是更适合做产品设计，UI 还是更适合做 UI 设计。不是说他们不能碰代码，而是每个人有自己的侧重点和擅长方向。

  3. 所以我们有了一个单独的原型仓库

    这个仓库的目标是和真实项目一比一同步，但技术架构不一样。它更像一个产品和设计可以直接动手的原型仓库。

    产品可以在上面设计原型，UI 可以在上面改设计，也可以先在 Figma 里弄完，再同步到这个仓库里。

  4. 这个仓库本身也在模拟真实产品

    里面有两个子项目，一个是外部端，一个是 App 端。理论上它们和真实项目完全同步，只是实现路径不同。

    这个背景很重要，因为后面很多问题，其实都是从这里开始的。

1、第一感受：真的很累 ​

现在写代码反而不是最慢的，真正累的是一个人同时要做很多角色。

1.1 迭代节奏被压缩了 ​

我先说我作为开发的感受：真的非常累。

以前我们等产品设计、等 UI、等需求确认。现在节奏被压得很紧，老板一开始说两天就要看一个迭代。

我不可能等产品都沟通完、设计完、评审完再开始做。很多时候只能先斩后奏，先把东西做出来，直接铺到上面，让老板先看到效果。

1.2 累的不是写代码，而是做判断 ​

很多需求其实不是全新的需求，很多都是抄。我们可以抄市面上已经存在的软件，但是我们的背景不一样。

我们做的是 AI Agent，还是结合 NAS 的产品。市面上没有完全一样的东西，只能找到一些相似的产品来参考。

即便是抄，我也不能只是抄界面。我汇报工作的时候，还是要跟老板说清楚：

  1. 这个需求为什么要这样做？
  2. 它存在的意义是什么？
  3. 别人为什么这么设计？
  4. 它背后的用户路径是什么？
  5. 有没有更好的办法？
  6. 结合我们当前项目的背景，我们自己的需求到底应该长什么样？

这些问题都要跟 AI 反复聊。聊对方产品为什么这么做，聊我们为什么不能照搬，聊我们有没有更好的路径。很多时候，一个上午就这么过去了。

AI 并没有改变研发流程的本质，但是它极大的压缩了这个过程，让你每天接触的信息密度空前的变大。

为了快速的实现目标，很多时候上面的 6 步可能只是几分钟就要做出判断，但是这 6 步可是一个都没有减少的。我们现在的决策依旧基于我们自身知识的积累，基于对于世界的认识，不把 coding 变为抽卡，掌控在自己的手下经验依旧重要，基础依旧是不可或缺的。

回到精力的问题，每一个需求里面，其实都包含了这些角色：

  1. 项目经理
  2. 产品经理
  3. 开发
  4. UI
  5. 测试
  6. 需求推进人

以前这些角色是分开的，现在很多时候都压到一个人身上。

所以后面我们也意识到，需求要更精细化。不是说不做大目标，而是每一个需求的颗粒度要变小。你可以先做一个方向，做完以后 UI 再跟进，产品再补充，最后再回补回来。

2、估时这件事也变了 ​

AI 让很多环节变快了，但它没有让边界、验证、真实数据这些东西消失。

2.1 不能只按测试时间算 ​

网上有个说法，说现在评估时间要以测试时间为标准。

我实际做下来觉得不是这么简单。

  1. 测试时间当然重要。
  2. 产品时间也被压缩了。
  3. 开发也没有变得不重要。

开发这个需求的时候，我们还是要确定边界，要设计架构，要看它跟其他模块有没有冲突。这些难道不是开发吗？这些其实是二次开发，是工程判断。

所以更准确地说，有 AI 之后，各个环节的实现路径都被压缩了，但不是某一个环节消失了。

2.2 方向性还是人要给出来 ​

产品可以借 AI 更快理解对方产品为什么这么设计，但是方向性还是人要给出来。

而这个方向性，恰恰是很多产品缺失的。很多产品只是老板的跟屁虫，老板说什么就是什么。

2.3 token 估时也不准确 ​

像李想他们说估 token，一个需求需要多少 token。但我觉得这个也不准确。

工作里有太多不确定因素。比如我为什么要让 AI 扫描整个仓库？因为我想知道当前需求和其他地方有什么关系，有什么边界，有没有冲突。这当然说得过去，但它会消耗很多 token。

所以：

  1. 按 token 算不合适。
  2. 按传统工时算也不完全合适。
  3. 更应该看需求靠近哪个风险层。

有些需求 AI 发挥得很好，本来估一天，可能一个小时解决了。但另外一些需求就不一定。你越靠近边界、状态、兼容性、真实设备、真实数据，它就越不稳定。

如何估时现在完全是薛定谔的事情。在没有 AI 的时候我们对于有经验的程序员要求也是估时要准确，因为很多需求拆解之后都是做过的，做过自然就可以尽量的靠近真实的完成时间。但是在 AI 时代完全不一样，你无法准确的评估。

所以我在想，估时还重不重要呢？因为他的完成时间一定是比之前快很多的，我们还需要纠结与一天两天的误差吗？是不是能够换一个维度呢？

AI 的到来既然能够重构团队协作方式，自然也能够重构软件流程的定义。

3、第二件事：我的改动影响到了别人 ​

我不是没测试，而是没有测到真实运行时的情况。

第二块，是我做的一个功能影响到了 AJ 的功能正常运行，然后他上来质问我。

其实我当时很不爽。

我心里第一反应是：我什么资历，你什么资历，你上来质问我？

他问我测试了吗？我当然测试了。我不是没测。我 mock 测试了，也解决了我那个 bug 上的问题。

但问题就在这里：

  1. 我测试的是我以为的问题。
  2. 不是它真实运行时的问题。
  3. 我没有测到真实情况。

这件事让我很难受，但它也很有价值。

3.1 不能只靠个人自觉 ​

这种问题该怎么解决？是靠我个人每次都更认真一点吗？是靠我每次写完都主动 review 他们的功能吗？

我现在确实会这么做。每一次我都会让 AI 帮我审查边界，提醒我不要影响其他人的逻辑，不要影响他们的功能。

但这不能只靠人。

万一换一个人呢？万一我离职了呢？下一个人是不是还会踩同样的坑？

3.2 要靠制度、rules、铁律 ​

所以这一定要靠制度，要靠 rules，要靠铁律。

最初级的就是CR 规范必须同步给所有人，不能只停留在我一个人的习惯里，更进一步的是走全自动化 e2e测试。

CR rules 这个随着团队业务的添加，会逐渐的添加，里面除了有放了一本代码好味道和坏味道，还是一个索引表，和 agent.md 一样，当我写的这个需求边界影响到了其他的业务模块的话，会有有留下一个：“动到了 xxx 的代码，需要阅读 docs/xxxxx 下面的规则”，里面可以是某一些字段如何使用，这个之前业务逻辑需要注意的地方。

当然这一个 docs 本来就是在 agent.md 有引入，CR 也是为了闭环整个写代码的环节。

4、我现在怎么理解工程化思维 ​

很多人说外行做不了 vibe coding，因为他们没有工程化思维。那工程化思维到底是什么？

工程化思维不是会写语法，而是会控制风险。 所谓的控制风险，就是要做到如下几个方面：

  1. AI 需要知道哪一些上下文？
  2. AI 需要知道多个需要之间交接上下文？
  3. AI 需要知道测试的重点是什么？你如何保证它的验证机制？
  4. Harness 工程如何实现保证可构建可控？
  5. AI 如何保持稳定的 Loop，并且持续的改进？
  6. AI 输出的多个方案，你要能够判断哪一个更加符合现状，判断不了，回到第一个问题，应该喂给他更加多的上下文。

不是你会不会写一个 for 循环，不是你会不会写 React，不是你会不会让 AI 生成一段代码。

真正的工程化思维，是你知道这个改动会影响谁，会在哪里坏，坏了以后怎么发现，怎么回滚，怎么证明它真的对。

4.1 工程化思维至少包含这些东西 ​

能力不是而是
拆问题一句“帮我做个功能”知道输入、输出、状态、异常、边界、依赖关系
看影响范围只看当前文件能不能跑知道它会不会影响 API、缓存、权限、老用户、部署、日志、回滚
定义正确性看起来能跑用测试、日志、灰度、验收用例、真实设备、真实数据证明它对
尊重已有系统一上来发明新架构先读现有模式，沿着项目已有习惯改
理解失败路径只处理成功流程想清楚网络失败、权限过期、数据为空、老版本客户端、设备不在线怎么办
会协作写完扔给别人小 PR、说明影响范围、写测试、接受 review、解释 tradeoff

4.2 外行是否绝对不能做 vibe coding？ ​

外行真正缺的，很多时候不是语法，而是：

  1. 不知道哪里危险；
  2. 不知道怎么验证；
  3. 不知道一个改动会波及谁；
  4. 不知道什么叫可维护；
  5. 不知道什么时候必须停下来找工程师 review。

AI 把写代码的门槛降了，但没有把负责后果的门槛降掉。AI Coding不是银弹。它是放大器，是一个杠杆，本来写代码的能力就是初中级程序员主要干得活。代码越多带来的混乱也只会越高。所以一个产品，一个设计想要实现一个高可用的系统，需要具备：

  • 能不能定义清楚问题。
  • 能不能写出高质量 SPEC。
  • 能不能设计合理的验证机制。
  • 能不能构建可控的 Harness。
  • 能不能让 AI 在 Loop 中持续改进，而不是持续跑偏。
  • 能不能判断 AI 的输出什么时候可信，什么时候只是看起来很合理。

有了这些能力，上面的问题自然迎刃而解。

而开发想要入门 设计，审美就是一个很大的门槛，如何把自己认为美的东西转为 Ai 能够理解的提示词就不是短时间可以做到。想要入门产品，产品思维，商业价值，对于用户需求的洞察力也不是问几句 AI 就可以能够提高的。

5、非研发需要走传统程序员进阶路线吗？ ​

那么非研发一定要负责AI Coding 呢，应该如何走这一条路？

不需要每个人都走“初级、中级、高级、架构师”那条老路，但也不是会跟 AI 聊天就能写生产代码。

不是每个人都要走以前那条路线：初级、中级、高级、架构师。不是说你不走完这条路，就永远不能写代码。

但是也不是说会跟 AI 聊天就能写生产代码。

更现实的能力分层为：

层级能做什么最低要求风险边界
第一层：能改小东西文案、样式、配置、简单页面、简单脚本会看 diff、会跑测试、会回滚不碰核心链路
第二层：能做窄功能表单、接口调用、数据展示、很窄的后台任务懂状态、错误处理、测试、权限、API 契约必须沿着已有模式改
第三层：能负责一个模块独立判断影响范围，写验收标准，处理线上反馈能和前后端、产品、设计、测试协作需要工程师 review
第四层：能改架构跨模块、数据模型、性能、安全、并发、部署、兼容性深工程经验不能靠 vibe coding 硬冲

但他们的价值不是替代工程师，而是：

  1. 用自己的领域理解；
  2. 加上 AI；
  3. 再加上基本工程纪律；
  4. 在有限范围内安全地产出。

简单来说，做到下面四点：

  1. 拆问题；
  2. 控风险；
  3. 做验证；
  4. 尊重系统边界。

6、这是初级程序员弯道超车的机会 ​

AI 给的是平均值和模板，人真正的价值是把舵。

初级的程序员还有活路吗？我无法从传统的晋升路线给出回答。

排除能够走垂直路线的程序员，那些已经不吃码农了。

只能是趁着产品和设计还没有开发那么熟料的使用 AI 工具的时候，快速的利用 AI成长，成为真正的技术架构师，成为一个有产品能力的产品经理，成为一个了解基本 UI 设计的设计师。

比如，当我们看到市面上有一些产品，或者在路边看到一些产品的时候，你需要思考说：

  • 这也有人买？
  • 到底什么样的人会买它？
  • 它如何解决用户的痛点的？

其实翻译成产品语言就是：它解决了什么需求？有这样需求的人多不多？前者是产品解决的痛点，后者就是它的商业价值了。解决的人的问题多，商业价值肯定高。然后你解决得好，赚的钱就越多，这也反过来证明你的产品是成功的。

在有了 AI 之后，我获取这些信息的路径就变得的简单很多，当然，重要的是我要要有自己的思考，AI 可以给我提供数据，可以作为我们自己的老师。

而这，就是我们普通程序员弯道超车的机会。

这世界其实对于每个人，或者说对于整个人类而言，都是一片黑暗的。我们并不足够了解这个世界，那个被点亮的世界，就像那里有一盏灯。我对世界的了解越多，点亮的灯就越多，这样我对世界的认识也就越多。

7、一个不太体面的真实想法 ​

短期我想保留自己的私域能力，长期团队又必须工程化、制度化。这里面有矛盾，但也不是完全无解。

最后还有一个真实但不太体面的想法。

我现在其实不想把我本地沉淀下来的 skill、rules、路径，全部提供给大家一起用。

这个想法很自私，我知道。

但人就是自私的。以后互联网圈可能会越来越多私域的东西。大家不会再无条件把自己的经验、规则、工具全部喂给 AI、喂给别人。

从个人角度讲，我当然希望自己沉淀得越多，别人犯的错越多，就越能凸显我的能力。

这句话听起来不好听，但它是真实的。

7.1 个人和团队之间的矛盾 ​

视角我真实的想法
个人角度我想保留自己的私域能力，让自己沉淀得更多，能力差距更明显。
团队角度真正要让团队稳定，还是要把 rules 建起来，把 CR 规范同步出去，把边界和验证变成制度。

所以这里有一个矛盾。

短期看，我想保留自己的私域能力。

长期看，团队必须工程化，必须制度化，必须让任何人接手都不至于把系统搞坏。

7.2 我现在更认可的边界 ​

后来我想了一下，这个想法不能简单地说对或者错。

它很真实，但它只能当情绪，不能当长期策略。

我不想把自己沉淀下来的东西全部共享出去，这个不丢人。因为这些东西确实是我用时间、错误、复盘换来的。AI 时代，谁能沉淀自己的工作流，谁就会和别人拉开差距。

但问题是，不是所有私域能力都适合私藏。

我现在更愿意把它分成三类：

类型我的处理方式原因
可以留在自己手里的东西个人判断模型、提问方式、拆需求习惯、审美、产品理解、工具链组合这些更像我的手感和经验压缩，就算共享出去，别人也不一定用得好
不应该私藏的东西CR 规则、事故教训、边界清单、测试要求、真实设备验证要求这些是团队安全网，不共享的话，别人继续踩坑，最后系统还是会坏
最值得长期沉淀的东西我持续形成新规则、新判断、新工作流的能力真正的护城河不是藏起来的 rules，而是我比别人更快形成 rules

所以更好的做法不是全部共享，也不是全部私藏。

更好的做法是：把安全底线制度化，把高级判断留在自己身上。

也就是说：

  1. rules、CR 规范、边界清单要同步；
  2. 事故教训要同步；
  3. 能避免团队重复犯错的东西要同步；
  4. 但是我怎么更快发现问题、怎么组合工具、怎么做产品判断，这些可以继续沉淀成我的个人优势。

这样想以后，我反而没那么纠结了。

完全私藏，短期可能显得我更强，但长期会让团队继续依赖我、消耗我，甚至最后出问题锅还是会回到我身上。

全盘共享，我又会觉得自己的优势被稀释。

所以我现在更认可一个中间态：

共享团队必须知道的底线，保留自己持续进化的判断力。

真正高级的优势，不是“我有一份别人没有的 prompt”，也不是“我藏了一套别人不知道的规则”。

真正高级的优势应该是：就算我把规则写出来，别人也只是照着做；但我能不断产出新的规则。

8、最后的结论 ​

All in AI 第一个月给我最大的感受是：AI 让实现变快了，但也把人的差距放大了。

谁能定义问题，谁能控制风险，谁能理解产品，谁能尊重系统边界，谁就更有机会成为那个真正把舵的人。
