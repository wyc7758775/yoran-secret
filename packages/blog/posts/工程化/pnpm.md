## PNPM解决了什么问题？

pnpm 就是了解决 npm 和 yarn的问题而诞生的，所以这个问题本质是在问题 npm 和 yarn 存在什么问题非解决不可。

### 依赖黑洞

NPM 早期版本存在的问题，有下面两个现象：

1. 循环嵌套

```js
node_modules
├─ pkg-a
│  ├─ index.js
│  └─ node_modules
│     └─ pkg-b
│        ├─ index.js
│        └─ node_modules
│           └─ pkg-a
│              └─ node_modules
│                 └─ pkg-b
│                    └─ node_modules
│                       └─ pkg-a
│                          └─ ...

```

pka-a 依赖 pkg-b, 然后 pkg-b 依赖 pkg-a。两个相互依赖，然后导致了死循环，无限创造自己。2020 年的开发依旧深受其害。

![1e2e948de0a29935ce70370e914a4d06.png](https://yoran-images-1256970527.cos.ap-guangzhou.myqcloud.com/%E4%BE%9D%E8%B5%96%E9%BB%91%E6%B4%9E%E9%97%AE%E9%A2%98.png)

> 截图来源 CNPM的 issue，地址为https://github.com/cnpm/cnpm/issues/321

2. 版本错配

```js
node_modules
├─ lodash@4.5.0
├─ pkg-foo
│  └─ node_modules
│     └─ lodash@3.6.0
├─ pkg-bar
│  └─ node_modules
│     ├─ lodash@3.6.0
│     └─ sub-a
│        └─ node_modules
│           └─ lodash@4.5.0
└─ pkg-baz
   └─ node_modules
      └─ sub-b
         └─ node_modules
            └─ lodash@3.6.0

```

上面是一个依赖包，它顶层有自己的`node_modules`。它的子依赖`pkg-foo`和`pkg-bar`，以及`pkg-baz`都有自己的依赖。当 install 到 `pkg-bar`的时候，发现自己的父依赖，既顶层的`node_modules`中的`lodash`版本不满足的自己的需求，所以就需要自己下载3.6.0 版本的。

这个时候这一整个依赖就有两个版本的。如果 `pkg-bar`自己的子依赖依赖的又是`4.5.0`版本的时候，**从下往上**找，找到自己的父级是`3.6.0`版本的，就自己下载`4.5.0`版本的。这就导致了重复的依赖下载的问题。

上面的两个问题轻則把这个 node_modules 包体积弄得很大，重則让操作系统直接卡死。好在这个问题npm 和 yarn 较早起版本就已经解决的问题。

npm 和 yarn 通过把依赖包平铺来解决这个嗯问题，同时也带来了下面的两个问题：幽灵依赖和依赖分身。

### 幽灵依赖

```js
import { b } from 'pack-1'
```

但是在`pakcages.json`中，没有`pack-1`的包。这个是你依赖的依赖引入的。

### 依赖分身
```js
node_modules
├─ lodash@4.5.0
├─ foo1
│  └─ node_modules
│      └─ lodash@3.6.0
├─ foo2
│  └─ node_modules
│      └─ lodash@3.6.0
└─ bar
```

npm 和 yarn 只会把一个版本拉到顶部，其他版本的依旧存在子依赖之中。

截止 25 年，NPM 和 Yran 基于为了兼容旧版本的问题，依旧没有解决这两个问题，优化了代码，提升了安装速度和体积占用问题，然并卵，主要矛盾不解决，意义不大。所以新项目找不到不使用 PNPM 的理由。

### pnpm 如何解决

它是通过【软链接和硬链接结合内容寻址存储，仅暴露声明依赖，并复用同版本包】解决了幽灵依赖和依赖分身的问题。

陌生的词非常的多，软链接、硬链接、内容可寻址存储这三个关键的计算都是操作系统的相关概念，对于前端理解困难非常的正常，只需要了解它们的效果即可。

用一张图来表达PNPM 中依赖包之间的关联：

![image.png|](https://yoran-images-1256970527.cos.ap-guangzhou.myqcloud.com/20250830200705609.png)

install 之后，依赖包的真正实体会安装到`./Library/pnpm/store/v3`当中，然后在项目的`node_modules`创建`.pnpm`文件，然后会创建对应的关联文件，关联到上面的实体中，里面的文件叫做硬链接。同层级的带着符号链接的，指向的是`.pnpm`中的文件，叫做软链接。

多个项目中同一个版本的硬链接指向的是同一个实体。

这样做的就带来如下好处：
1. 所有项目中的依赖都平铺在`/pnpm/store`之中，不同版本之间只存储 diff/patch版本，极大的降低了所有项目占用的内存的同时，还解决了 npm 依赖分身的问题。
2. 软链接中只保存当前项目写在`pakcage.json`中的依赖，直接解决了幽灵依赖的问题。

## 为什么不直接在NPM或者yarn上面直接升级呢？

1. pnpm 属于对 npm 的重构，底层逻辑都不一样，所以这个所以重建一个项目效果更加好。
2. npm 需要兼容旧的版本，这个也是它不改变的理由。
3. npm 毕竟是别人的东西，挂着别人的名字。
