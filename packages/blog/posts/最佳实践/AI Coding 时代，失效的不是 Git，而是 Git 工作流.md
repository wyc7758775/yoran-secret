# AI Coding 时代，失效的不是 Git，而是 Git 工作流

## 当前的 Git 已经不适用于我们现在 AI 革命的形式了

当前的 Git 已经不适用于我们现在 AI 革命的形式了。

更准确一点说，Git 不一定要删掉，它可以更新换代，我们依旧可以用 Git，但是需要新增一些新的命令、新的流程来适配。

首先明确一点，我们的 Git 不是为了解决多人协作的问题。多人协作本身不是问题，所以正确的描述应该是：**Git 是多人协作的工具**。

这个工具解决了多人协作的什么问题？这才是 Git 存在的意义。

以前没有协同工具的时候，多个人在一个代码仓库里面操作，怎么知道谁改了什么？怎么知道什么时候改的？怎么合并？怎么回退？怎么解决冲突？

Git 很好地解决了这些问题。

但是现在的问题变了。

我们需要知道以前没有协同工具的时候，多人协作在一个代码仓库如何进行操作。有了协同工具，它们又有什么样的问题，有什么样的痛点。只有总结出这两块，才真正知道 Git 现在面临的一个问题，也就是它解决的问题。

## AI 时代，commit 的价值正在下降

我现在觉得，适配 Git 不重要，也是因为一些分支管理、一些 commit 的规范不重要了。

现在冲击最大的是 commit 的规范。

以前 commit 很重要。一个 commit message 写得好不好，能不能描述清楚这一次变更，是代码协作里面非常重要的一环。

但是现在不一样了。

现在很多代码都是 AI 生成的，人不一定真的看每一条 commit。即便它带着很清晰的 message，你也不一定明白这次 diff 背后的真实意图。

每天的 PR 和 commit 都有可能流于形式。

以前出现了 BUG，可以通过 Git 来看是谁改的，当初为什么改。现在还需要这个流程吗？我觉得这个问题是需要重新思考的。

因为 AI 生成的代码里，commit message 很可能只是“看起来规范”。它不一定真的承载了人的判断，也不一定真的能帮助下一个人理解这次修改。

所以我现在的判断是：

**commit 是代码账本，但它不应该再承担所有协作上下文。**

真正重要的东西从“每一条 commit 写得漂亮”，变成了：

- 这次改动整体想解决什么问题？
- AI 到底改了什么？
- 哪些地方需要人重点判断？
- 怎么验证它没有破坏以前的功能？
- 如果出问题，怎么知道这次变更的边界在哪里？

也就是说，commit 的价值正在下降，意图和验证的价值正在上升。

## 问题不是 Git，而是 Git 工作流太依赖程序员经验

现在最矛盾的点是，Git 的 commit 这个流程没有必要承担那么多东西了。

其他的一些复杂多段协作流程也可能不重要。

它其实为了我们提交 MVP 的速度，可以极大地简化。

所有人都共用一个基线，只要知道哪个人开发的、什么时候开发的、这次改动解决什么问题、有没有影响以前的功能，这就可以了。

这也是因为我们现在的迭代不是双周了。它没有那么明确的概念，它甚至是两周的一个迭代、内部迭代、两天一个小版本、一天一个小版本。

所以我们要解决的问题就是：这两天或者一个大的版本，它有没有影响到以前的功能。

但是这跟 Git 有关系吗？

没有那么大关系。

这跟测试用例、单测、构建、验证流程有关。

Git 只是记录了代码历史，但它不能告诉你这个功能是不是还能用。它能告诉你谁改了文件，但它不能天然告诉你为什么这么改、怎么验证、风险在哪里。

## Smart Commit 想解决什么问题

所以我想做的不是替代 Git，而是在 Git 上面加一层新的协作语义。

这个东西就是 Smart Commit。

Smart Commit 解决的问题不是“帮程序员少敲几个 git 命令”。如果只是这样，它的价值太低了。

它真正解决的是：

**在 AI Coding 时代，把一次代码提交从一堆 commit，变成一份可以被人理解的变更说明。**

以前我们可能会一次性提交十几条 commit。

但是这些意图、业务意图真的会有人看吗？

大概率不会。

真实场景里，人通常只看三样：

- 最终 diff
- PR 描述
- CI、测试、自测说明有没有过

所以如果把 `Intent`、`Change Set`、`Risk`、`Validation` 全部塞进每一条 commit message，最后很可能还是没人看。

它会变成另一种高级形式主义。

因此 Smart Commit 的方向不是让每条 commit 都变得很长，而是：

- commit 保持短，只记录这一小块是什么
- 一次推送结束后生成一份 Change Report
- Change Report 放到 PR 描述里，成为人真正看的入口

commit 是账本，PR 里的 Change Report 才是协作说明书。

## Change Report 是什么

Change Report 不是 Git 原生就有的东西，也不是以前项目里已经存在的东西。

它是 Smart Commit 这个 skill 新增的一种输出约定。

每次 smart commit 执行完提交和推送后，都生成一段“本次变更报告”。

它大概长这样：

```md
Intent:
本次推送整体想解决什么问题。

Change Set:
- 改了哪些模块
- 每组变更解决什么问题

Validation:
- 执行了哪些验证
- 哪些没验证，为什么

Risk:
- 可能影响哪里
- 人需要重点看哪里

Commits:
- hash + commit message
```

这个东西第一版可以只出现在 Codex 对话窗口里。

但更合理的是放进 PR 描述里。

因为人审代码的时候，本来就应该看 PR，而不是一条一条翻 commit。

## PR 流程为什么重要

如果要让产品和 UI 也开始写代码，那 PR 流程就更重要了。

因为他们现在连分支的概念都不懂，也不知道创建分支，也不知道为什么我们需要创建分支。这些基本的概念都没有。

这不是他们的问题。

以前写代码是程序员的事情，所以 Git 的复杂性被默认丢给程序员消化。现在 AI 让产品、UI、运营都可能直接改代码，这些人不应该被要求先学完整套 Git。

但是他们也不能直接往主分支提交。

主分支可以理解成“大家现在共同依赖的稳定版本”。

分支可以理解成“我先在旁边开一个临时工作区”。我可以在这个工作区里让 AI 修改代码、生成页面、改样式、补文案。只要它还没有合并回主分支，就不会影响其他人。

PR 就是把这个临时工作区拿出来给别人看：

- 我改了什么
- 为什么这么改
- 有没有验证
- 有没有风险
- 是否允许合并回主分支

所以 PR 不是形式主义。

PR 是“把代码变更交给团队确认”的入口。

Smart Commit 要做的事情，就是把这些 Git 概念藏到后面，让产品和 UI 不需要先理解所有命令，也能走一条相对安全的协作路径。

他们只需要说：

```text
smart commit，走 PR 流程
```

然后 Smart Commit 做这些事：

1. 如果当前在 `main`，自动创建一个 `codex/xxx` 分支
2. 根据业务意图分析 diff
3. 把相关文件分成几组 commit
4. 推送分支到 GitHub
5. 生成 Change Report
6. 用 Change Report 创建 PR 描述

这样，产品和 UI 不一定需要立刻懂 Git 的全部概念，但他们提交出来的东西依旧是团队可以审查、可以回滚、可以追踪的。

## 它面向的用户是谁

Smart Commit 不是只面向资深程序员的。

它更像是给 AI Coding 时代的新协作者准备的。

第一类是程序员。

程序员当然懂 Git，但是现在 AI 一次性改很多文件，commit 容易变成流水账。Smart Commit 可以帮程序员把 diff 按业务意图拆开，再生成一份可以直接放进 PR 的说明。

第二类是产品和 UI。

他们已经开始直接写代码了。

他们可能不懂分支、不懂 commit、不懂 PR，但是他们懂需求、懂界面、懂用户体验。AI 帮他们把代码写出来以后，真正缺的是一条安全进入工程协作的路。

Smart Commit 对他们的价值不是“教会他们 Git”，而是先让他们用一种不容易把主分支搞坏的方式参与进来。

第三类是小团队。

小团队最容易出现一种情况：大家都知道 Git 很重要，但是流程太重没人执行；流程太轻又容易出事故。

Smart Commit 可以把流程收敛成一句话：

```text
把这次改动整理成 PR。
```

剩下的分支、提交、推送、PR 描述，都交给工具完成。

## 最后

我现在越来越觉得，AI 时代不是把所有旧工具都删掉。

更重要的是怀疑以前所有固有的工作经验。

Git 还在，分支还在，commit 还在，PR 还在。

但是它们的重心变了。

以前我们围绕 commit 工作。

现在我们应该围绕任务意图工作。

以前我们要求人写规范的 commit。

现在我们应该让 AI 帮我们生成完整的 Change Report，让人把精力放在判断风险、验证结果、确认是否合并。

所以 Smart Commit 不是一个“自动提交工具”。

它更像是 AI Coding 时代的一层协作适配器。

它解决的不是 Git 命令太难的问题，而是：当越来越多不熟悉 Git 的人开始通过 AI 写代码时，我们如何让他们安全地进入团队协作流程。

这才是它真正要解决的问题。

# Smart Commit

此 skill 帮助代理智能地将代码更改分批提交，并把一次推送的业务意图、变更范围、验证结果和风险集中成一份 Change Report。

**重要：执行此 skill 时，直接分析、提交并推送，无需询问用户确认。**

默认行为：
- 如果当前分支是 `main` / `master` / `release`，自动进入 PR 模式，先创建 `codex/<简短任务名>` 分支
- 如果当前分支已经是功能分支，则提交并推送当前分支
- 若用户提到 `PR`、`Pull Request`、`创建 PR`、`走 PR 流程`，无论当前在哪个分支，都进入 PR 模式
- 只有用户明确要求“直接推当前分支”时，才跳过 PR 模式

## 工作流程

### 1. 获取当前更改
- 检查 git 状态：`git status`
- 获取完整差异：`git diff`（工作树）和 `git diff --staged`（已暂存）
- 识别未跟踪文件；明显的临时目录或构建产物（如 `tmp/`、`dist/`、`.vitepress/dist/`、`node_modules/`）不要自动加入提交
- 如果有未暂存的有效更改，自动暂存相关文件

### 2. 分析更改内容

分析文件变更，优先按**业务意图**分组，其次才按文件或技术类型分组。常见分组维度：
- **业务意图**：这组变更在解决同一个用户问题、产品问题或工程问题
- **功能模块**：相同功能模块的文件分为一组
- **变更类型**：
  - ✨ 新功能 (feat)
  - 🐛 修复 bug (fix)
  - 📝 文档 (docs)
  - 🎨 样式 (style)
  - ♻️ 重构 (refactor)
  - ⚡ 性能 (perf)
  - ✅ 测试 (test)
  - 🔧 构建/工具 (chore)
  - 🚀 部署 (deploy)
  - 💄 `ui` - UI 样式更新
- **文件关联**：具有依赖关系的文件应放在一起

分组时同时记录每组的：
- `Intent`：为什么要改
- `Change Set`：实际改了什么
- `Validation`：应该如何验证，或已经执行了什么验证
- `Risk`：可能影响哪里

### 3. 生成 Commit Messages

commit message 保持短小、可扫读，不要把完整业务意图塞进每一条 commit。完整说明放到最后的 Change Report。

使用以下格式：

```
<图标> <类型>(<范围>): <简短描述>

Change-Set: <本组变更的短标识，可选>
```

常用图标与类型映射：
- ✨ `feat` - 新功能
- 🐛 `fix` - 修复 bug
- 📝 `docs` - 文档
- 🎨 `style` - 样式（不影响功能）
- ♻️ `refactor` - 重构（既不是新功能也不是修复）
- ⚡ `perf` - 性能优化
- ✅ `test` - 测试
- 🔧 `chore` - 构建过程或辅助工具变动
- 🚀 `deploy` - 部署
- 💄 `ui` - UI 样式更新

### 4. 执行分批提交（全自动）

对于每个分组：
1. 添加相关文件：`git add <files>`
2. 创建提交：`git commit -m "<message>"`
3. 继续下一个分组

### 5. 推送到远程

所有 commit 创建完成后：
1. 获取当前分支名：`git branch --show-current`
2. 直接推送到远程：`git push origin <branch-name>`
3. 输出 Change Report，而不是只输出 commit 列表

### 5B. PR 模式

当用户要求走 PR 流程时：
1. 检查当前分支；如果在 `main` / `master` / `release` 上，先创建新分支，分支名使用 `codex/<简短任务名>`
2. 分批提交后推送新分支：`git push -u origin <branch-name>`
3. 生成 Change Report 作为 PR body
4. 如果本机安装了 GitHub CLI 且已登录，执行：
   `gh pr create --base main --head <branch-name> --title "<简短标题>" --body-file <临时 PR 描述文件>`
5. 如果没有 `gh`，输出 GitHub Compare URL 和完整 PR body，让用户在浏览器创建 PR

PR title 使用本次变更的整体意图，不要简单复用某一条 commit message。

### 6. 输出 Change Report

每次 smart commit 完成后，必须在最终回复中输出一份面向人类阅读的 Change Report。它是本次推送的真正审阅入口。

格式：

```
Change Report

Intent:
本次推送整体想解决什么问题。

Change Set:
- 按业务意图列出本次推送包含的几组变更
- 每组说明影响的模块和关键文件

Validation:
- 已执行的验证命令及结果
- 未执行的验证需要说明原因

Risk:
- 可能受影响的功能
- 需要人工重点看的地方

Commits:
- <hash> <message>
```

原则：
- 人应该主要看 Change Report，不需要逐条阅读十几条 commit
- commit 是代码账本，Change Report 是协作说明书
- 如果用户要开 PR，Change Report 可以直接作为 PR 描述草稿
- PR 模式下，Change Report 必须进入 PR 描述；最终回复中同时给出 PR URL 或 Compare URL

## 重要约束

- **全自动执行**：无需用户确认，直接分析、提交、推送
- **保护主分支**：默认不要直接向 `main` / `master` / `release` 推送；先创建功能分支，再走 PR
- **每次只处理一个分组**：按顺序处理每个分组
- **不要合并不相关的更改**：如果某些更改不属于任何逻辑分组，单独处理
- **不要提交临时文件**：未跟踪的临时目录、构建产物和缓存文件默认忽略
- **原子性提交**：每个 commit 应该只包含一个逻辑变更
- **清晰的描述**：commit 描述应该简洁，Change Report 承载完整上下文
- **避免形式主义**：不要为每条 commit 编写冗长模板；超过 3 条 commit 时，更要把意图汇总到 Change Report

## 示例

假设有以下更改：
- `src/app/page.tsx` - 添加新功能组件
- `src/app/lib/utils.ts` - 添加新工具函数
- `README.md` - 更新文档
- `src/styles/globals.css` - 样式调整

分析后直接执行：
1. `git add src/app/page.tsx src/app/lib/utils.ts && git commit -m "✨ feat(app): 添加新功能"`
2. `git add README.md && git commit -m "📝 docs: 更新 README"`
3. `git add src/styles/globals.css && git commit -m "🎨 style: 调整全局样式"`
4. `git push origin main`
5. 输出：

```
Change Report

Intent:
完成应用新功能的最小可用实现，并补齐使用说明和样式表现。

Change Set:
- app 功能：新增页面组件和工具函数
- docs：更新 README
- style：调整全局样式

Validation:
- 未执行自动化验证；当前任务仅完成提交推送

Risk:
- 新工具函数调用方较少，重点检查边界输入
- 全局样式可能影响其他页面

Commits:
- <hash> ✨ feat(app): 添加新功能
- <hash> 📝 docs: 更新 README
- <hash> 🎨 style: 调整全局样式
```
